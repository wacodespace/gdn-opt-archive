01

优化背景

做这件事的场景和动机

Qwen3-Next/Qwen3.5 decode 的瓶颈层之一就是 GDN 递推。Triton 版受限于编译器的调度能力（无法显式控制 cp.async 流水与 warp 布局），带宽利用率不满。CuTe DSL 提供接近 CUDA C++ 的控制力但保留 Python JIT 分发的灵活性，适合放进 jit_kernel 体系。

02

好处与收益

  • Decode GDN 算子层面优于 Triton fused_recurrent 路径（配套 benchmark 见 bench_cutedsl_gdn）。小 batch 场景受益于 SM 占用改善尤其明显。
03

Trade-off

正确性债、分叉和退化
  • 平台窄：依赖 CUTLASS DSL + Hopper 级特性（cp.async），CUDA-only，ROCm/老架构不可用；默认关闭需 env 开启。
  • JIT 首编译延迟：首个请求触发编译，冷启动毛刺；按形状缓存意味着 batch 形状多样时编译多次。
  • 维护成本高：1500 行手写 kernel，后续布局改动（如 K-last/VK 布局）都要双份适配；CI 中曾因 flaky 被临时跳过 cutedsl 性能测试，说明数值/性能稳定性打磨成本真实存在。
