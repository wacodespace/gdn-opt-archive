01

优化背景

做这件事的场景和动机

Chunked prefill + prefix cache 场景下，每个 chunk 结束都要持久化 SSM 状态；而 kernel 反正要在 epilogue 里把 b_h 寄存器块写显存，写到"池里的原位置"和写到"临时张量"代价相同——搬运本身可以被 kernel 的必要写出吸收。这是把内存管理语义（gather/scatter）下沉进计算 kernel 的典型做法。KDA（Kimi）路径同步适配。

HIP / Qwen3.5 上 chunk 流水的另一头也在收 launch：T >= 64 时把 chunk_local_cumsum + chunk_scaled_dot_kkt 融成 fused_cumsum_kkt，solve_tril 换成 16×16 分块 solve_tril_16x16_kernel，再和 fused_merge_recompute 一起把 stage-one 从 4 个 kernel 压到 3 个。中间量 A 少一次完整读写。

02

好处与收益

  • 每层每 chunk 省：一次 h0 gather 拷贝 + 一次 final_state 分配 + 一次 scatter 写回（约 3× 状态大小的带宽 + 2 次 kernel launch）。收益随 batch、GDN 层数、chunk 数线性放大。
  • HIP 长序列 prefill 上，chunk stage-one 少一次 kernel 和一轮中间张量往返。
03

Trade-off

正确性债、分叉和退化
  • Kernel 现在对全局状态池做原地读写，别名与生命周期约束外移：调用方必须保证同一槽位不会在同一 forward 中被两个序列引用，prefix cache 复制状态时也必须与该语义配合（后续 修 prefix-cache 复用时 KV/VK slot_layout 失步 属于同一类状态池一致性问题）。
  • 接口签名变化（output_final_state → initial_state_indices，不再返回 final_state），所有调用方（含 KDA）需同步迁移；与上游 FLA 库的接口分叉，rebase 成本增加。
  • h0 由 gather 后的连续内存变为按 index 间接寻址，kernel 内多一次索引 load，可忽略。
  • fused_cumsum_kkt 只在 T >= 64 启用，短序列走旧路径，同一模型两条 chunk 流水。
  • solve_tril 的 16×16 分块 + merge 是精度敏感区：下三角求逆的数值稳定性跟着分块走，HIP 路径必须做端到端精度回归。
