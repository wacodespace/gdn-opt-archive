01

优化背景

做这件事的场景和动机

GDN decode 是典型的小 kernel 长链条：每层几十个微小算子，launch-bound。凡是形状为 [bs, heads] 级别的逐元素计算，融合的收益 ≈ 省掉的 launch 次数。这两个门控在数学上无依赖交叉（都只读投影输出 a/b 和常量参数），融合无正确性风险。

HIP / Qwen3.5 上同一思路有 prefill 形状版：fused_gdn_gating_and_sigmoid 一次算出 g 和 beta。同批还把两次独立的 l2norm_fwd 收成 fused_l2norm_qk，一个 kernel 同时归一化 q 和 k。

02

好处与收益

  • 端到端最多 0.85% 提升（decode 场景，单算子层面省 2 次 kernel launch × 每 token × 48 层 GDN）。
  • HIP prefill 门控同样 2 次 launch → 1 次；q/k L2 norm 少一次 launch。
03

Trade-off

正确性债、分叉和退化
  • Kernel 假设 a/b 连续布局（offset 用 i_b * seq_len * NUM_HEADS 计算）。后来 Qwen3.5 引入 fused projection 之后 a/b 变成 strided split view，这个隐含假设导致 gating 读错内存、精度损坏，由 stride-aware kernel 重启投影融合 加 stride 参数修复——是本融合的直接技术债。
  • g/beta 输出固定为 fp32 / 输入 dtype，与原实现一致，无精度损失。
  • HIP 的 prefill gating / fused_l2norm_qk 与 CUDA Triton 路径分叉，两套数值实现要各自回归。
